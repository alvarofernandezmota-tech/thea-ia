Problema 3: BaseRepository TypeError ⚠️ MEDIO
Síntomas:

python

Causa Raíz:

BaseRepository.create() tenía parámetros posicionales fijos

tenant_id no estaba en la firma del método

Solución:

python
# base_repository.py

# ANTES (Demasiado rígido)
async def create(self, tenant_id: str, **data: Any) -> T:
    data['tenant_id'] = tenant_id
    instance = self.model(**data)
    # ...

# DESPUÉS (Flexible)
async def create(self, **kwargs) -> T:
    """
    Create a new instance.
    
    Args:
        **kwargs: Any fields required by the model
        
    Returns:
        Created instance
    """
    instance = self.model(**kwargs)
    self.session.add(instance)
    await self.session.flush()
    await self.session.refresh(instance)
    return instance

🎓 LECCIONES APRENDIDAS (PROFUNDO)
1. Windows + asyncpg: El Desafío Principal
Problema:
Windows usa ProactorEventLoop por defecto, que no es compatible con asyncpg debido a diferencias en cómo manejan I/O de sockets.

Aprendizaje:

python
# SIEMPRE configurar en Windows:
if asyncio.sys.platform == 'win32':
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
Por qué funciona:

SelectorEventLoop usa select() system call (compatible con sockets)

ProactorEventLoop usa IOCP (Windows-specific, incompatible con asyncpg)

Señales de este problema:

AttributeError: 'NoneType' object has no attribute 'send'

Errores en asyncpg.protocol.protocol.BaseProtocol._write

Event loop closed errors

2. pytest-asyncio: Gestión de Event Loops
Problema:
pytest-asyncio por defecto reutiliza event loops entre tests, causando problemas cuando conexiones de BD quedan abiertas.

Aprendizaje:

python
# Crear nuevo loop POR FUNCIÓN:
@pytest.fixture(scope="function")
def event_loop(event_loop_policy):
    loop = asyncio.new_event_loop()
    asyncio.set_event_loop(loop)
    yield loop
    loop.close()
Beneficios:

Cada test tiene loop limpio

No hay estado compartido

Errores aislados por test

3. Fixtures: Orden de Ejecución es Crucial
Problema:
Tests fallan con FK violations porque fixtures no declaran dependencias.

Aprendizaje:

python
# ❌ MAL: Sin dependencias explícitas
@pytest_asyncio.fixture
async def event_tools(db_session):
    tools = EventTools(db_session)
    return tools

# ✅ BIEN: Con dependencia explícita
@pytest_asyncio.fixture
async def event_tools(db_session, test_user):  # ← test_user se ejecuta primero
    tools = EventTools(db_session)
    tools.set_context(user_id=123, tenant_id="test_tenant")
    return tools
Regla de Oro:
Si Fixture B necesita que Fixture A se ejecute primero, declarar A como parámetro de B.

4. BaseRepository: Flexibilidad vs Tipo Safety
Dilema:
Parámetros posicionales dan type safety pero son inflexibles. **kwargs son flexibles pero pierden type hints.

Solución Adoptada:

python
# Flexibilidad en BaseRepository
async def create(self, **kwargs) -> T:
    """Flexible para cualquier modelo"""
    instance = self.model(**kwargs)
    # ...

# Type safety en Service Layer
async def create_event(
    self,
    user_id: int,
    tenant_id: str,
    event_data: EventCreate  # ← Type safety aquí
) -> Event:
    return await self.event_repository.create(
        user_id=user_id,
        tenant_id=tenant_id,
        **event_data.model_dump()
    )
Filosofía:

Repository: Flexible (low-level)

Service: Type-safe (high-level)

6. PostgreSQL Real vs Mocks: Cuándo Usar Cada Uno
Decisión Tomada:
Usar PostgreSQL real para tests E2E.

Ventajas:

Tests más realistas

Detecta problemas de FK reales

Valida queries SQL reales

Detecta problemas de transactions

Desventajas:

Tests más lentos (~9s vs ~1s con mocks)

Necesita DB running

Cleanup más complejo

Conclusión:
Vale la pena para tests E2E críticos. Usar mocks para tests unitarios.

7. Schemas Pydantic: Validación Temprana Salva Tiempo
Ejemplo del Problema:

Ventaja de Pydantic:

python

Lección:
Validar en el edge (schemas) previene bugs downstream.
